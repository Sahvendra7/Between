# Between Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Between, which works like this:
1. An AI turns a synthetic co-parenting agreement into cited rules.
2. Both parents approve them.
3. A deterministic engine decides each expense.
4. The owing parent pays the other parent's PayPal sandbox account through an Orders v2 checkout.
5. Between verifies the payment against PayPal in a tamper-evident record.

**Architecture:**
- One FastAPI service with Jinja2 templates over SQLAlchemy Core: SQLite locally, Render Postgres hosted.
- Pure modules (money, agreement, validate, engine) are ported from the spike with its tests.
- I/O modules (extraction, payments, reconcile, record, access) sit behind small interfaces, and the web layer composes them.

**Tech Stack:** Python 3.12, FastAPI, Jinja2, python-multipart, SQLAlchemy 2 Core, psycopg 3 (binary), httpx, anthropic (official SDK), pydantic 2, pypdf, pytest. P1: `@bryntum/calendar-community@8.0.0` (MIT), vendored.

**Spec:** `docs/superpowers/specs/2026-11-11-between-design-r2.md`.
- The spike code it ports from: `~/Desktop/PayPal/spike/` (`ai/rules.py`, `ai/keys.py`, `ai/test_rules.py`, `ai/extract.py`, `paypal_spike.py`, `webhook_server.py`, `evidence/`).
- Kitty source to copy from (**read only, never modify**): `~/Desktop/Switch/Kitty/kitty/access.py`, `kitty/pot.py` (`chain_next`, `chain_tag`, `chain_check`), `app/ui/kitty.css`, `app/ui/fonts/`.

## Global Constraints

- Repo root: `~/Desktop/PayPal/between/`. All paths below are relative to it. **Never write to `~/Desktop/Switch/Kitty`.**
- PayPal base URL is fixed: `https://api-m.sandbox.paypal.com`. There is no live-mode code path.
- PayPal flow: Orders v2 `intent=CAPTURE`, `purchase_units[0].payee.email_address` = the receiving parent.
- **Never used:** holds, Payouts, or refunds by Between.
- **Wording:**
  - Call it a "PayPal sandbox checkout", never "Friends & Family".
  - Label fees "estimate" before capture and "from PayPal" after.
  - Label resolutions: "Your working arrangement in Between. It does not change your legal agreement."
- **Models:** `claude-sonnet-5-5` (rules, P1 schedule) and `claude-haiku-5-5` (receipts).
  - No `temperature`, `top_p` or `top_k`.
  - `max_tokens` is 16000 for extraction and 1024 for receipts.
  - Use `client.messages.parse(..., output_format=<Pydantic model>)`.
- Money is integer cents everywhere; amounts never come from the model unconfirmed.
- **Logs** hold ids, hashes, timings and error codes only. Never agreement text, quotes, prompts, model output or receipt content.
- **Receipt bytes** are never written to disk or the DB.
- **Invites** expire after 72 h and rotate on re-issue.
- **Cookies:** `HttpOnly`, `SameSite=Lax`, `Secure` when `BETWEEN_SECURE_COOKIES=1`, 14 days.
- **CSRF** token on every POST except `/webhooks/paypal`.
- **Demo mode** (`BETWEEN_DEMO_MODE=1`):
  - agreements must contain `SYNTHETIC DOCUMENT FOR SOFTWARE TESTING`;
  - PayPal emails must end in `@personal.example.com` or `@business.example.com`;
  - receipts ≤ 2 MB, PNG/JPEG/PDF;
  - agreement text ≤ 60,000 characters;
  - a banner on every page.
- **Timeline** (owner-confirmed): feature freeze **Thu 12 Nov, 12:00 IST**; submission target **Thu 18:00 IST**; hard deadline **Fri 13 Nov, 01:30 IST**.
- **Git:** run `git init` in Task 1. Commit steps are written as checkpoints, but **don't commit until the owner authorizes commits, and never push without the owner's go-ahead.**

### Task 3: Rulesets: versions, both approvals, private answers, resolutions

**Interfaces:**
- **Consumes:** `validate.validate`, `validate.check_resolution`, `engine` (for the hash only, via `ruleset_hash`), `record.append`, `record.Actor`.
- **Produces:**
  - `ruleset_hash(rs: dict) -> str`: canonical JSON of `{parties, rules sorted by id, questions}`, sha256.
  - `create_version(conn, family_id, agreement_id, validated: dict, parties: dict, actor) -> dict`: returns `{"id", "version", "hash", "json"}` and appends an event `ruleset.created`.
  - `approve(conn, ruleset_id, role, hash_seen, actor) -> None`: raises `RulesetError("stale_version")` if `hash_seen` isn't the version's hash, or `"not_latest"` if a newer version exists; appends `ruleset.approved`.

  - `submit_answer(conn, ruleset_id, question_id, role, choice: str, value: str | None, actor) -> None`: one row per (ruleset, question, role); an upsert until both have answered, then refuses with `RulesetError("locked")`.
  - `answers_for(conn, ruleset_id, question_id, viewer_role) -> {"mine": dict | None, "other": dict | None, "both_answered": bool}`: `other` is None unless both answered.
  - `options_for(question: dict) -> list[dict]`: deterministic templates per spec §6.2. Each `{choice, label, makes_rule: dict | None}`. `missing_number` options take `value` (days).
  - `resolve_if_agreed(conn, family_id, ruleset_id, actor) -> dict | None`: for every question where both answered with equal `(choice, value)` and `makes_rule` is not None, adds a resolution rule (`id = "R<n>"`, `origin = "resolution"`, `source = {question_id, answered_by: ["A","B"], answered_at}`). Each rule must pass `check_resolution`. If any were added, it calls `create_version`. Returns the new version, or None.
